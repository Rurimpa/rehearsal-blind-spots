# 予行演習では見えないもの

**子分AIを使った予行演習では、「止まることで現れる失敗」は出てこない。**

子分AIは人に聞いて止まらない。窓も出さない。別勘定にも載らない。**その3つでできている失敗は、予行演習では原理的に見えない**——起きにくいのではなく、**起こりようがない**。

English: [README.md](README.md)

## すぐ使う

自分の `CLAUDE.md` か `AGENTS.md` に、次をそのまま貼ってください。

```markdown
## 子分AIで予行演習するとき
- 予行演習の結果を信じる前に、気にしている失敗それぞれについて「これは何かが止まることで現れるか」を問う。
  （許可や承認を待つ・費用・窓が出ない・同じ名前の会話が2つできる・会話の記録が保存されない）
- 「はい」なら、予行演習が無事に終わっても何の証拠にもならない。その部分は本物の会話で試す。
- 予行演習で確かめてよいのは中身のほう（手順の順番・指示があいまいでないか・役割の重なり）。
```

使い方：

1. 本番の前に、気にしている失敗を書き出す。
2. そのうち「何かが止まることで現れる」ものに印を付ける。
3. 印を付けたものだけ本物で試し、残りは予行演習で確かめる。

これだけです。実際に起きたことと限界は下に書いてあります。

---

## 何が困るのか

費用のかかる多エージェントの手順を本番で回す前に、安く予行演習しておこう、と考えるのは自然である。子分AIを何体か立てて役を演じさせ、壊れるところを見つけて直し、それから本番をやる。

**中身についてはうまくいく。制約についてはうまくいかない。**

子分AIは、本物のセッションの小型版ではない。親の権限の中で動き、目の前に人間がおらず、窓を持たず、承認も拒否もされない。**そして、多エージェントの手順が実際に壊れるのは、まさにその面である。**

だから予行演習はきれいに終わり、「手順はできている」という結論になる。できていない。**もともと危なくなかった半分だけを試したことになる。**

## 実際に起きたこと

同じ手順を2回回した。1回目は子分AI5体での予行演習、2回目は本物のセッション5席で、人がキーボードの前にいる状態。

| | 予行演習（子分AI5体） | 本番（5席） |
|---|---|---|
| **席が「参加してよいか」を人に聞いて止まる** | **0件**——子分AIは権限で止まらない | **5席中3席。人が3回操作した** |
| **参加手順に何を書くべきか** | 既存の条文の寄せ集め。命令の核心（**可能な限り人の承認なしに進める**）に、1行も答えていなかった | 核心が出た——**呼ばれたら人に諮らず答える。人の承認が要るのは、答えたあとに実装・正本の変更・送信が発生するときだけ** |
| **無人で起こすと画面に窓が出ない** | 出てこなかった | ある席がすでに実測を持っていた。**3通りの起動方法すべてで、窓のハンドルが0** |
| **手順を自動化するときの費用の歯止め** | 出てこなかった | すぐに指摘が出た。**議案にも、前回の決定にも、1行も無かった** |

4件。**4件とも本番から出た。予行演習からは1件も出ていない。**しかも1件目は運の問題ではない——**子分AIには聞く相手の人間がいないので、「席が止まって人に聞く」は起こりようがない。**

**これは n=1 である。**1つの手順、1つの作業場、1組の実行。統制実験ではなく現場の観察である。

## 見分け方

予行演習を信じる前に、気にしている失敗それぞれについて、1つだけ問う。

> **その失敗は、何かが「止まる」ことで現れるか。**

**はい、なら、子分AIの予行演習では見えない。本物でやる。**

止まることで現れる失敗には、少なくともこれだけある。

- **権限・承認**——席が人を待って止まり、人がいない。あるいは、いて「だめ」と言う
- **費用**——実行が拒否される、絞られる、あるいは単に高くついて誰かが止める
- **見え方**——セッションは立っているのに窓が出ない。出ても誰も見ていない場所に出る
- **名前と宛先**——2つのセッションが同じ名前になる。メッセージが別の相手へ届く
- **記録**——セッションは動いているのに、会話の記録が保存されていない

**予行演習が得意なこと**は別にある——中身の形、工程の順番、指示が一意に読めるか、役割が重なっていないか。そこは本物の効用があり、やる価値がある。**ただ、きれいに終わった予行演習を、上の一覧についての証拠として読まないこと。**

## なぜそうなるのか

子分AIは、親へ答えを返すために立てられる。**止まらないように、全部が整えられている。**

- 親の権限をそのまま引き継ぐので、人に確認を出すはずの呼び出しの多くが、そのまま通る
- 対話できる端末がつながっていないので、人の判断が要ることは、勝手に決着するか、黙って失敗する
- 窓もタブも、他のセッションが宛先にできる名前も持たない
- 費用は親にまとめられるので、別の歯止めに引っかからない

**1つずつは、まっとうな設計である。合わさると、予行演習は「制約を外した状態」で走っていることになる**——そして制約こそが、試したかったものである。

知っておくとよい公開の記録がある。子分AIの権限まわりには固有の不具合報告がある（親の権限設定を継承しない／権限の確認が人に出ないまま黙って失敗する／入れ子の権限確認が永久に止まる）。**それらは不具合であり、直るかもしれない。ここで言っているのは別のことで、直っても消えない**——**完璧に動く子分AIであっても、止まって聞く相手の人間がいない。**

## 限界

- **n=1。**1組の実行。頻度を報告しているのではない。
- **版によって変わる。**子分AIが権限とツールをどう扱うかは版によって変わり、公開されている報告どうしですでに食い違っている。**この表を信じるのではなく、自分の版で確かめること。**
- **予行演習をやめろという話ではない。**予行演習は安く、今回も**中身**については本物の問題を見つけている。主張は狭い——**きれいに終わった予行演習は、「止まる形の失敗」についての証拠にならない**、というだけである。
- **本番は実際に金と人の注意を使う。**予行演習が存在する理由がそれである。**上の見分け方は、本番を使うべき場所に本番を使うためにある。**

## 先行研究

- **多エージェントの失敗の分類**は存在し、有用である。7つのフレームワークを横断した広く引用される研究では、失敗モードのおよそ3分の2が、個々のエージェントではなく**連携**の側にあるとされている。
- **子分AIの権限の不具合**は、公開の課題管理に記録がある（親セッションから権限を継承しない／権限の確認が人に出ないまま失敗する／入れ子の権限確認が止まったままになる）。
- **エージェントの試験の指南**は、各エージェント単体・受け渡しごと・全体を負荷をかけて、の3層で試すことを勧めている。ある解説は、**予行演習は「承認で止まって待つ」を再現しない**と1行だけ触れている。
- **見つからなかったのは、これを「選び方の規則」として述べたもの**——**予行演習という手段そのものが、ある種類の失敗を観測不能にしている**という指摘と、そこから出てくる問い（**その失敗は止まることで現れるか**）で本番にすべき回を決める、という形。
- **見つからなかったことは、無いことの証明ではない。**先行するものをご存じなら Issue を立ててほしい。明記する。
